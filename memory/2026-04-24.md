### 教训
- exec 命令参数格式问题：直接在 command 里 cd 到目标目录即可，不要传错误的 workdir 参数。今天因为这个问题循环执行了十几次无效命令，浪费了大量轮次。

## 2026-04-24 - 飞书群聊配置备忘

飞书群聊通信的关键配置项（channels.feishu）：
- `groupPolicy`: "open" 或 "allowlist"
- `groupAllowFrom`: 用户 OpenID 列表（不是群 ID！）
- `groups.*.requireMention`: false 表示免@模式
- `plugins.entries.feishu.enabled`: true（群聊需要这个）

之前的故障是因为 groupAllowFrom 填了群 ID 而不是用户 OpenID，以及 requireMention 放在了根级别而不是 groups 对象内。

## 2026-04-24 - 分页系统分析

用户要求梳理四个二级页面（games/books/artworks/hiyamaxtm）底部的翻页按钮。

**核心问题：**

1. **不统一** — 四个页面各自复制粘贴了完整的分页 HTML/CSS/JS，没有提取成 `_includes/pagination.html` 公共组件
2. **硬编码 bug** — games 和 hiyamaxtm 的 JS 中写了 `const totalPages = 1`，超过 9 个条目时分页按钮永远只显示 1，但实际会翻页到空白页
3. **设计不安全** — 20 页时数字按钮总宽度约 976px，没有省略号逻辑，没有 overflow 保护，768px 以下屏幕会溢出/换行

**四个页面的分页代码状态：**

| 页面 | totalPages 计算 | 状态 |
|------|----------------|------|
| games | `const totalPages = 1` ❌ 硬编码 | 有 bug |
| books | `Math.ceil(cards.length / cardsPerPage)` ✅ 动态 | 正常 |
| artworks | `Math.ceil(cards.length / cardsPerPage)` ✅ 动态 | 正常 |
| hiyamaxtm | `const totalPages = 1` ❌ 硬编码 | 有 bug |

**建议修复：**
1. 提取公共组件 `_includes/pagination.html`
2. 修复 games/hiyamaxtm 的硬编码 totalPages
3. 超过 10 页时启用省略号逻辑（如 `1 ... 5 6 7 ... 20`）
4. 移动端加 `overflow-x: auto` 或缩小按钮

## 2026-04-24 - artworks 详情页图片加载优化

**问题：** 用户反馈 artworks 详情页加载太慢。

**根因：** 详情页直接加载 3024×4032 原图，单张 2-3MB，29 张原图总共 66MB。

**解决方案（三级图片体系）：**

```
原图 (3024×4032, ~2.5MB)     → 存档用，不直接加载
  ↓ 缩放至 1200px
中等尺寸 (1200×1600, ~450KB)  → 详情页加载
  ↓ 缩放至 384px
缩略图 (384×512, ~30KB)       → 列表页卡片加载
```

**执行结果：**
- 生成 29 张 1200px 中等尺寸图: `assets/images/artworks/medium/`
- 总大小: 58.4MB → 13.1MB（省 78%）
- 单张平均: ~2.5MB → ~450KB
- `_layouts/artwork.html` 更新为加载中等尺寸图
- 添加 `loading="eager"` + `decoding="async"` + `width="1200"`

## 2026-04-24 - artworks 详情页加载慢问题排查

**用户反馈：** artworks 详情页图片加载极慢，以 https://hiyascott.github.io/hiyamax-home/artworks/splash-of-joy/ 为例。

**排查过程：**
1. 确认 `_layouts/artwork.html` 已正确加载 medium 尺寸图（476KB）✅
2. 测试图片加载速度：`curl -w` 测得 476KB 图片加载耗时 **26 秒**

**根因：** 不是图片尺寸问题，是 **GitHub Pages 访问速度问题**。服务器在海外，从国内访问经常慢或不稳定。

**提供的解决方案：**

| 方案 | 操作 | 效果 |
|------|------|------|
| A (推荐) | 开启 Cloudflare CDN（免费） | 全球加速，国内访问提升明显 |
| B | 图片迁移到国内图床 | 最快，但增加维护成本 |
| C | 使用 GitHub + jsDelivr 代理 | 临时方案，免费但可能不稳定 |

**结论：** 之前的 medium 尺寸图优化（58.4MB→13.1MB）在代码层面是正确的，但网络链路瓶颈限制了实际体验。需要用户选择 CDN 方案。
